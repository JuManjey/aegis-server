# AEGIS relay — протокол клиент↔сервер (§0 / §7.6 / §12.2)

> Авторитетное описание контракта между `aegis-client` (Android-клиент) и
> `aegis-server` (этот репозиторий). Любое изменение формата обязано быть
> согласовано в обоих репозиториях (§0). Клиентская сторона: `network-tor/…/
> RelayClient.kt`, `app/…/messaging/RelayReceiver.kt`, `RelayGateway.kt`, вывод
> mailbox-id — `rust/aegis-core/src/psk.rs::mailbox_id`.

## 1. Модель и границы доверия (zero-trust к серверу, §10.9)

Сервер — **недоверенный участник**. Он НЕ видит:

- plaintext сообщений/сигналинга (двойной E2EE: слой A каскад на PSK + слой B Signal);
- личности пользователей в конвертах переписки (accountId, identity-ключи серверу
  не передаются; исключение — ящик заявок удалённого добавления, §4.7);
- ключи (секрет слоя A обменивается вне сети — `aegis-client/docs/psk_exchange.md` —
  либо **выводится** из подписанного рукопожатия RCH и в сеть не уходит,
  `aegis-client/docs/contact_requests.md`).

Связь «кто-кому» сервер напрямую не получает (нет аутентификации по личности,
дроп анонимный), но **защита метаданных от самого сервера неполная** (известное
ограничение, аудит 01.11.2026). Сервер видит и хранит:

- непрозрачный `mailbox` (256-бит), шифртекст конверта и время приёма;
- **открытые поля конверта** — он хранится как BLOB, но это обычный JSON: тип
  канала (`channel`: сообщение / сигналинг звонка / служебное событие / `keyx` /
  синхронизация своих устройств), тип Signal-сообщения (PreKey = новая сессия),
  признак слоя A, номер устройства-отправителя и `msgId`, одинаковый во всех
  копиях сообщения для устройств получателя (выдаёт их число и связывает их
  ящики). Длина не выравнивается — размер текста и вложений виден почти точно;
- **общую Tor-цепочку клиента**: клиент не изолирует потоки и держит отдельный
  long-poll на каждый контакт, поэтому все его опросы и отправки приходят по
  одной rendezvous-цепочке. Оператор, пометив цепочки своим tor-демоном
  (например, `HiddenServiceExportCircuitID`) или просто по таймингу, может
  связать ящики пользователя и восстановить устойчивый псевдонимный граф
  «кто-кому» (id ящиков статичны, пока жив PSK);
- в канале удалённого добавления — `accountId` отправителя заявки и ответившего;
- бессрочно — список всех использованных id ящиков со счётчиком сообщений
  (`mailbox_seq`, §5).

Для доставки этого достаточно; для анализа связей — тоже, пока клиент не
изолирует потоки и не уберёт служебные поля внутрь шифрования.

### 1.1 Что добавляет каталог обнаружения (§4.7/§4.8) — честно

| Режим | Что появляется на сервере | Перечислимо |
|---|---|---|
| Приватный каталог (`AEGIS_DIRECTORY_ENABLED=1`, по умолчанию) | опаковый `index` (256 бит из тега) + **запечатанная** запись; ключа у сервера нет | нет |
| Публичные алиасы (`AEGIS_ALIAS_ENABLED=1`, по умолчанию ВЫКЛ) | `HKDF(ник)` + **открытая** подписанная заявка: `accountId`, Ed25519-ключ, указатель на приватный каталог | **да**, словарём по никам |

Инвариант, который сохраняется в ОБОИХ режимах: сервер **не может подменить
ключи**. `accountId = SHA-256(ed25519_pub)[..16]` — коммитмент к ключу, и клиент
проверяет и подпись, и эту привязку сам (fail-closed). Поэтому даже полностью
скомпрометированный сервер способен лишь отказать в обслуживании, но не провести
MITM. Приватный каталог вообще ничего не добавляет к тому, что сервер уже видел
(опаковый id + шифртекст); публичные алиасы — добавляют, и именно поэтому
выключены по умолчанию и решаются оператором.

## 2. Адресация: mailbox из PSK (без метаданных)

Каждая 1:1-переписка имеет общий PSK (обменян вручную, §6.2). Из него обе стороны
детерминированно выводят **пару направленных идентификаторов очередей**:

```
mailbox(role) = HKDF-SHA512(salt="AEGIS/mailbox/v1", ikm=PSK,
                            info="aegis/mailbox/v1/role/" + role)   // 32 байта
role ∈ {0, 1}
```

Роль определяется сравнением публичных identity-ключей Signal сторон
(лексикографически по base64): у кого ключ «меньше» — тот **role 0**, у другого —
**role 1**. Тогда:

- я **слушаю** (long-poll) `mailbox(myRole)` — это мой входящий подканал;
- я **пишу** (POST) в `mailbox(peerRole)` = `mailbox(1 − myRole)` — входящий
  подканал собеседника.

Обе стороны вычисляют одинаковую пару, но каждая читает свою половину и пишет в
чужую → по самим id сервер не может связать их с личностью или между собой
(связать их можно по Tor-цепочке и открытым полям конверта — см. §1). Сам id
(256 бит энтропии из PSK) — это **capability**:
не зная PSK, вычислить/угадать mailbox невозможно, поэтому отдельная
аутентификация в v1 не нужна (сервер и так недоверенный и не нарушает
конфиденциальность E2EE).

Идентификатор в URL — **URL-safe base64 без паддинга** (43 символа для 32 байт),
алфавит `[A-Za-z0-9_-]`, длина 8..64.

> Текущий клиент для переписки использует per-device адресацию v2
> (`aegis-client/docs/multidevice.md` §4): `HKDF-SHA512(salt="AEGIS/mailbox/v2", ikm=PSK,
> info="aegis/mailbox/v2/conv/<accountId>/<deviceId>")` — свой входящий ящик у
> каждого устройства. Схема v1 выше в клиенте больше не используется; для
> сервера разницы нет — это такие же непрозрачные id.

## 3. Транспорт

API и БД одни и те же; у клиента ровно два режима сети, и транспорт строго
следует режиму — **без перекрёстного отката** (в режиме Tor клиент никогда не
идёт по HTTPS напрямую, в режиме без Tor никогда не поднимает Tor):

- **Tor ВКЛ (по умолчанию).** Весь трафик идёт через встроенный Tor клиента
  (Arti, SOCKS5) к Onion Service v3 релея. Внутри Tor — **обычный HTTP/1.1** (Tor
  уже даёт шифрование и аутентификацию сервиса; полезная нагрузка вдобавок E2EE).
  TLS поверх onion не требуется (§12.3). По умолчанию клиент подключается к
  `<hs>.onion:443` (порт onion форвардит на relay:8080). Tor недоступен → запросы
  не уходят вовсе (fail-closed).
- **Tor ВЫКЛ (явный выбор пользователя).** HTTPS к тому же релею:
  `https://<домен>` → Caddy → relay:8080 (клирнет-профиль, `README.md`).
  TLS не ниже 1.2, цепочка и имя хоста проверяются системным хранилищем;
  дополнительно — пины SPKI из подписанного конфига (§4.6), если они заданы.
  HTTP/1.1, `Connection: close`, без редиректов, кэша и cookie. Сервер в этом
  режиме видит реальный IP клиента; релей его не получает — фронт вырезает
  `X-Forwarded-For`/`Forwarded`/`X-Real-IP`, а журнал доступа фронта выключен.
  Сквозное шифрование от режима не зависит.

Собеседники в разных режимах работают через одну БД и видят сообщения друг друга.

## 4. Эндпоинты

Базовый префикс — `/v1`. Все ответы — JSON (кроме `GET /prekeys` — тело бандла).

| Метод | Путь | Назначение |
|---|---|---|
| `GET`  | `/v1/health` | Статус сервиса (healthcheck) |
| `GET`  | `/v1/params` | Какие каталоги включены и сложность PoW |
| `POST` | `/v1/mailbox/{id}` | Положить конверт в очередь (анонимный дроп) |
| `GET`  | `/v1/mailbox/{id}?after={seq}&wait={sec}` | Long-poll приём |
| `POST` | `/v1/mailbox/{id}/ack` | Подтвердить обработку (удалить `seq ≤ upto`) |
| `PUT`  | `/v1/prekeys/{id}` | Опубликовать публичный prekey-бандл (§7.6) |
| `GET`  | `/v1/prekeys/{id}` | Получить prekey-бандл (путь keys.overSignal) |
| `PUT`  | `/v1/blob/{id}` | Загрузить зашифрованный блоб вложения (§14.4) |
| `GET`  | `/v1/blob/{id}` | Скачать блоб вложения |
| `DELETE` | `/v1/blob/{id}` | Удалить блоб (после подтверждённого приёма) |
| `PUT`  | `/v1/directory/{index}?ttl={sec}` | Опубликовать запечатанную запись каталога (§4.7) |
| `GET`  | `/v1/directory/{index}` | Получить запечатанную запись каталога |
| `DELETE` | `/v1/directory/{index}` | Снять запись каталога с публикации |
| `PUT`  | `/v1/alias/{index}` | Занять/продлить публичный алиас `@ник` (§4.8) |
| `GET`  | `/v1/alias/{index}` | Получить подписанную заявку на алиас |
| `GET`  | `/v1/turn` | Эфемерные TURN-креды для медиа звонков: onion-TURN и клирнет STUN/TURN/TURNS (§7.5) |
| `GET`  | `/v1/config` | Подписанный офлайн адрес релея (авто-обнаружение, §12.2) |

### 4.1 `POST /v1/mailbox/{id}`
Тело — **сырые байты** конверта (`WireEnvelope` / `CallWireEnvelope` /
`ControlWireEnvelope` в JSON, но для сервера это непрозрачный BLOB). Клиент
демультиплексирует принятые конверты по внутреннему полю `channel`
(`""`=текст / `"call"`=сигналинг звонка / `"control"`=метаданные переписки §14.2/§7.3),
но серверу это поле не важно — он хранит и отдаёт конверт как есть (channel-agnostic).
Релей конверт не разбирает, однако прочитать открытые поля (`type`, `layerA`,
`msgId`, `senderDevice`, `channel`) он может — см. §1.
Ответ: `{"seq": <int>}` — порядковый номер в очереди. Лимит тела —
`AEGIS_MAX_BODY_BYTES`. Переполнение очереди сверх `AEGIS_MAX_QUEUE` вытесняет старейшие.

### 4.2 `GET /v1/mailbox/{id}?after={seq}&wait={sec}`
Возвращает конверты с `seq > after`, по возрастанию. Если новых нет и `wait > 0`,
соединение держится до появления конверта или до `wait` секунд (кап
`AEGIS_MAX_WAIT_SECS`). Ответ:
```json
{ "items": [ { "seq": 7, "dataB64": "…", "ts": 1731000000 } ], "next": 7 }
```
`next` — максимальный `seq` в ответе (или `after`, если пусто) — курсор для
следующего запроса. `dataB64` — стандартный base64 конверта.

### 4.3 `POST /v1/mailbox/{id}/ack`
Тело: `{"upto": <int>}`. Удаляет обработанные конверты `seq ≤ upto`. Ответ:
`{"acked": <int>}`. Клиент вызывает после успешной расшифровки/сохранения.

### 4.4 Prekeys (опционально, только для keys.overSignal — §8/§10.12)
`PUT` тело = JSON публичного prekey-бандла (формат — `aegis-client/docs`,
`nativeSignalDemoPreKeyBundleJson`). `GET` отдаёт последний опубликованный бандл
или `404`. Для пресета «Параноик» (по умолчанию) НЕ используется — бандл там
приходит без сервера-каталога ключей: identity — в QR при встрече, сам бандл —
по каналу `keyx` поверх слоя A (`aegis-client/docs/psk_exchange.md` §3). Перезаписать опубликованный
бандл может любой, кто знает `id` (смягчено закреплением identity на клиенте).

### 4.4a Blob вложений (§14.4)
Крупные вложения (фото/видео/файлы) не помещаются в конверт mailbox (лимит
`AEGIS_MAX_BODY_BYTES`), поэтому хранятся отдельными блобами. Для сервера блоб —
**непрозрачный шифртекст** (каскад слоя A на случайном 256-битном ключе); ключ и
`id` едут к получателю ВНУТРИ сообщения (`AttachmentRef` в конверте mailbox), сервер
их не видит. `id` — тот же формат capability, что и mailbox (URL-safe base64 без
паддинга, 256 бит, длина 8..64), **генерирует клиент**.

- `PUT /v1/blob/{id}` — тело = сырые байты шифртекста
  (`Content-Type: application/octet-stream`). Отдельный лимит `AEGIS_BLOB_MAX_BYTES`
  (дефолт 12 МБ). Ответ: `{"ok": true}`.
- `GET /v1/blob/{id}` — отдаёт байты шифртекста (`application/octet-stream`) или
  `404`, если блоба нет (не загружен / просрочен по TTL / удалён).
- `DELETE /v1/blob/{id}` — удаляет блоб. Клиент вызывает после успешного
  скачивания+расшифровки+сохранения (минимизация хранения §7.3). Ответ:
  `{"deleted": <int>}`.

Блобы чистятся тем же sweeper'ом по жёсткому потолку **7 суток** (§5), даже если
`DELETE` не пришёл (получатель офлайн).

**Потолки хранения — ДВА, как у конвертов**: по числу (`AEGIS_MAX_BLOBS`, дефолт
2000) и по суммарному объёму (`AEGIS_MAX_BLOB_BYTES_TOTAL`, дефолт 1 ГиБ). При
превышении любого вытесняются самые старые блобы. Потолка по числу одного
недостаточно: `AEGIS_MAX_BLOBS × AEGIS_BLOB_MAX_BYTES` — это до 24 ГиБ, то есть
вложения были бы единственным способом переполнить диск, зная лишь onion-адрес
(у конвертов байтовый потолок есть и равен 512 МиБ).

### 4.4b Голосовые сообщения (§14.4)

**Отдельных маршрутов нет и не нужно.** Голосовое — это обычное вложение: звук
(AAC-LC в контейнере ADTS, `audio/aac`) шифруется каскадом слоя A на случайном
256-битном ключе и грузится через `PUT /v1/blob/{id}`, а ссылка едет внутри
конверта mailbox. Сервер **не знает, что вложение голосовое**: и длительность, и
огибающая лежат под слоями A+B (zero-trust §7.6/§10.9).

`AttachmentRef` внутри конверта расширен **аддитивным** полем `voice`:

```json
{
  "objectId": "<43 симв. url-safe base64>",
  "keyB64": "<base64 256-бит ключа каскада>",
  "fileName": "voice-message.aac",
  "mimeType": "audio/aac",
  "sizeBytes": 18432,
  "kind": "FILE",
  "voice": { "durationMs": 7400, "waveformB64": "<75 симв. base64>", "v": 1 },
  "v": 1
}
```

- `durationMs` — длительность, замеренная отправителем при записи. Она в
  приоритете над оценкой платформы: для потока ADTS длительность считается по
  битрейту и на переменном битрейте врёт.
- `waveformB64` — огибающая громкости: **ровно 56 байт** (по одному на отрезок
  записи, шкала 0..255) в base64 без паддинга → 75 символов. Позволяет получателю
  нарисовать полоски ДО скачивания блоба; иначе входящее голосовое выглядело бы
  пустой полосой, а считать огибающую локально можно только полным проходом
  AAC-декодера. Пустая строка допустима (клиент подставит синтетическую).

**Совместимость версий** — почему `kind` остаётся `FILE`, а не становится
`AUDIO`. Конверт разбирается с `ignoreUnknownKeys = true`, но **без**
`coerceInputValues`: неизвестное ПОЛЕ старый клиент молча пропускает, а
неизвестное ЗНАЧЕНИЕ ENUM уронило бы разбор всего `WireContent` — и сообщение
откатилось бы на «сырой текст», то есть пользователь увидел бы в ленте служебный
JSON вместо сообщения. Поэтому:

| Отправитель | Получатель | Что видит получатель |
|---|---|---|
| новый | новый | плеер с дорожкой и таймкодом |
| новый | старый | обычная карточка файла `voice-message.aac` с кнопкой «Скачать» — звук скачивается и расшифровывается штатно |
| старый | новый | `voice` отсутствует → `null`, поведение прежнее |

Признак «это голосовое» на стороне клиента — наличие `voice`, а не `kind`.
Аудиофайл, выбранный пикером (`audio/*` без `voice`), тоже получает плеер, но
огибающая для него синтезируется детерминированно из `objectId`.

### 4.5 `GET /v1/turn` — TURN-креды для медиа звонков (§7.5/§10.10)
Выдаёт **эфемерные** креды для coturn: TCP-TURN через отдельный onion (режим
Tor) и/или клирнет STUN/TURN/TURNS того же coturn (режим без Tor). Анонимно (как
mailbox): знание адреса релея — достаточная capability. TURN включён, когда
задан `AEGIS_TURN_SECRET` и хотя бы один адрес — `AEGIS_TURN_ONION` или
`AEGIS_TURN_PUBLIC_URIS`; иначе `404`. Ответ:
```json
{
  "onion": "<coturn-hs>.onion",
  "port": 3478,
  "username": "1731003600:9f3c…",
  "credential": "base64(HMAC-SHA1(secret, username))",
  "realm": "aegis",
  "ttl": 3600,
  "expiry": 1731003600,
  "stun": "relay.example.com:3478",
  "uris": [
    "stun:relay.example.com:3478",
    "turn:relay.example.com:3478?transport=udp",
    "turn:relay.example.com:3478?transport=tcp",
    "turns:relay.example.com:5349?transport=tcp"
  ]
}
```
`onion` — пустая строка, если onion-TURN не настроен (тогда звонки в режиме Tor
не начинаются — fail-closed).
Схема coturn `use-auth-secret` (TURN REST API): `username = "<expiry>[:<nonce>]"`,
`credential = base64(HMAC-SHA1(static_auth_secret, username))`. `static_auth_secret`
знают только релей и coturn — **клиенту он не раскрывается** (тот получает лишь
производные креды на срок `ttl`).

**`uris`** (аддитивное поле, массив строк; пустой = не раздаётся, старые клиенты
его игнорируют) — клирнет ICE-серверы своего coturn из `AEGIS_TURN_PUBLIC_URIS`:
только схемы `stun:`, `turn:`, `turns:`; некорректные элементы релей отбрасывает
при запуске и пишет об этом в журнал. Креды `username`/`credential` общие для
`turn:`/`turns:` и onion-TURN; `stun:` идёт без кред.

**`stun`** (аддитивное поле; пустая строка = не раздаётся) — устаревший адрес STUN
`host:port` из `AEGIS_STUN_PUBLIC`. Его используют старые клиенты при выключенном
«медиапотоке через Tor»; новые — только как запасной STUN в режиме без Tor, если
в `uris` STUN нет.

**Как клиент это использует** — маршрут медиа выводится из режима сети:

- **Tor ВКЛ.** RTP работает по UDP, Tor несёт только TCP, поэтому клиент
  форсирует ICE-политику **RELAY** и поднимает локальный TCP-форвардер
  `127.0.0.1:<port>` → SOCKS5(Tor) → `<coturn>.onion:port`, отдавая WebRTC
  единственный ICE-сервер `turn:127.0.0.1:<port>?transport=tcp`. Ни STUN, ни
  host-кандидатов, ни серверов из `uris`/`stun`. Если креды или onion-TURN
  получить не удалось (404, пустой `onion`, Tor/релей недоступны), звонок клиент
  **не начинает**: без ретранслятора WebRTC отдал бы собеседнику свои IP.
- **Tor ВЫКЛ.** ICE-политика **ALL**, серверы — из `uris` (запасной вариант —
  `stun`), причём только на домене HTTPS-адреса релея или его поддоменах:
  STUN третьих сторон получил бы IP пользователя, а недоверенный сервер не
  должен направлять телефон в loopback, локальную сеть или onion-имя. Без
  серверов звонок соединится только в пределах одной локальной сети.

**Собеседники в разных режимах.** Клиент с Tor собирает только relay-кандидат,
клиент без Tor — host, srflx и relay. Работает пара relay↔relay: обе аллокации
живут на одном coturn, и пересылка между ними — доставка внутри сервера (адрес
ретрансляции внутренний, `external-ip` не задаётся). Ретранслировать в чужие
адреса coturn не даёт: разрешена только пересылка в собственные аллокации.

**Zero-trust.** Медиа сквозное (DTLS-SRTP + кадровый AES-GCM) — coturn
ретранслирует ТОЛЬКО шифртекст. Пиры в режиме Tor приходят из Tor (реальный IP
скрыт); отдельный onion от релея → сервер не связывает трафик релея и TURN между
собой. Пиры в режиме без Tor приходят с реальных IP (согласие — в диалоге
выключения Tor); журнал coturn в клирнет-профиле выключен.

### 4.6 `GET /v1/config` — авто-обнаружение адреса релея (§12.2)
Чтобы пользователь **не вводил адрес релея вручную**, клиент периодически
(транспортом текущего режима — через Tor или по HTTPS) запрашивает подписанный
конфиг-документ. Если раздача не задана
(`AEGIS_CONFIG_DOC`/`AEGIS_CONFIG_SIG` пусты) → `404` (клиент остаётся на зашитом
в сборку адресе по умолчанию). Ответ:
```json
{
  "doc": "<base64 каноничных байт JSON payload>",
  "sig": "<base64 Ed25519-подписи над этими байтами>"
}
```
`doc` (после base64-декодирования) — JSON payload:
```json
{ "v": 2, "relays": ["<hs>.onion"], "minAppVersion": 2,
  "relaysHttps": ["https://relay.example.com"],
  "httpsPins": ["sha256/C5+lpZ7tcVwmwQIMcRtPbsQtWLABXhQzejna0wHFr8M=",
                "sha256/diGVwiVYbubAI3RW4hB9xU8e/CH2GnkuvVFZE8zmgzI="],
  "turnOnion": "<turn-hs>.onion", "turnPort": 3478 }
```

**`relaysHttps`** (аддитивное) — тот же релей по HTTPS (`https://host[:port]` без
пути) для режима без Tor; клиент берёт первый корректный адрес. **`httpsPins`**
(аддитивное, необязательное) — пины SPKI `sha256/<base64 от 32 байт>`; рукопожатие
проходит, если ключ хотя бы одного сертификата проверенной цепочки совпал с
пином. Пиньте ключи корней CA (у Let's Encrypt — ISRG Root X1 и X2), а не листа:
ключ листа меняется при продлении. Адрес и пины применяются только вместе; к
адресу, введённому пользователем вручную, пины из конфига не применяются. Нет
`httpsPins` — только системная проверка цепочки и имени. Старые клиенты новые
поля игнорируют, поэтому для смешанного парка документ обязан содержать и
`relays`. Подписывает `aegis-config-sign sign ... --relay-https <url>
[--https-pin <pin>]...`.

**Модель доверия (zero-trust, §10.9).** Приватного ключа подписи на сервере
**нет** — `doc`/`sig` генерируются ОФЛАЙН-инструментом `aegis-config-sign`
(`--features tools`) на доверенной машине оператора и вставляются в `.env`.
Клиент проверяет подпись **зашитым в APK** публичным ключом Ed25519 (`BuildConfig
.RELAY_CONFIG_PUBKEY`) ДО применения адреса. Поэтому даже полностью
скомпрометированный сервер не может подменить адрес релея. Дополнительно onion
v3 самоаутентифицируется (адрес = публичный ключ HS), а контент защищён E2EE
(слои A/B) независимо от того, какой релей выбран.

**Защита от отката.** Клиент принимает документ только со **строго большей**
`v`, чем ранее применённая (`configVersion`). Ротация адреса = увеличить `v` и
переподписать. `minAppVersion` позволяет мягко потребовать обновления клиента.

**Fail-closed.** Нет зашитого pubkey / не прошла подпись / битый JSON → адрес НЕ
меняется. Ручной адрес пользователя (`relayManual`) авто-обновление не трогает.

> В текущей сборке клиента (0.4.2) публичный ключ не зашит
> (`aegis.relayConfigPubkey` пуст), пины SPKI тоже не заданы — авто-обнаружение
> по `GET /v1/config` неактивно, клиент работает на адресах из сборки или
> введённых вручную.

### 4.7 Каталог обнаружения — удалённое добавление контакта (RCH v1)

Полное описание протокола — `aegis-client/docs/contact_requests.md`. Роль сервера
минимальна и **не требует доверия**.

Клиент выводит из своего 256-битного **тега обнаружения** три значения
(`aegis-client/rust/aegis-core/src/discovery.rs`):

```
index      = HKDF-SHA512(salt="AEGIS/discovery/v1", ikm=tag, info="aegis/discovery/v1/index")
record_key = HKDF-SHA512(salt="AEGIS/discovery/v1", ikm=tag, info="aegis/discovery/v1/record-key")
invite_box = HKDF-SHA512(salt="AEGIS/mailbox/v2",   ikm=tag,
                         info="aegis/mailbox/v2/invite/<accountId>/<deviceId>")
```

- `PUT /v1/directory/{index}` — тело: **сырые байты** запечатанной записи
  (`nonce || XChaCha20-Poly1305(record_key, payload, aad="aegis/discovery/v1/record/"||index)`).
  `?ttl=<сек>` — желаемый срок публикации, клемпится `AEGIS_DIRECTORY_MAX_TTL_SECS`.
  Ответ: `{"ok":true,"expiresIn":<сек>}`. Лимит — `AEGIS_DIRECTORY_MAX_BYTES`.
- `GET /v1/directory/{index}` — отдаёт те же байты (`application/octet-stream`)
  или `404`.
- `DELETE /v1/directory/{index}` — снимает с публикации; идемпотентно.

**Zero-trust.** Сервер видит опаковый `index` (256 бит) и шифртекст. Он не знает
ни чья это запись, ни что внутри; каталог **неперечислим** (индекс
невоспроизводим без тега). Перезаписать запись может только владелец тега —
знание `index` и есть capability, как и для mailbox. Оговорка: следующий шаг
рукопожатия раскрывает больше — INVITE в ящик заявок несёт `accountId`
отправителя открытым текстом, ответ — `accountId` ответившего
(`aegis-client/docs/contact_requests.md` §10), так что факт заявки между двумя
аккаунтами сервер видит.

Внутри записи (после расшифровки клиентом) — JSON, который клиент проверяет
**fail-closed, все пункты обязательны**:

```json
{ "v":1, "accountId":"aegis:<32 hex>", "ed25519":"<64 hex>", "x25519":"<64 hex>",
  "nickname":"…", "fingerprint":"<64 hex>",
  "devices":[{"deviceId":1,"signalIdentity":"<b64>","bundle":{…}}],
  "tagCommitB64":"<b64 SHA-256(label||tag)>",
  "issuedAtMs":0, "expiresAtMs":0, "sigB64":"<b64 Ed25519>" }
```

1. AEAD открылся под `record_key` → публикатор знал тег;
2. `sigB64` верна под `ed25519`;
3. `account_id_from(ed25519) == accountId` — **привязка accountId к ключу**;
4. `accountId` совпал с тем, что пользователь получил в адресе вне сети;
5. `tagCommitB64 == SHA-256(label || tag)` — запись выпущена для ЭТОГО тега;
6. `expiresAtMs > now`, `issuedAtMs` не откатился относительно кэша.

> Расхождение клиента 0.4.2 с п. 6: запись с `expiresAtMs ≤ 0` клиент считает
> бессрочной (`DirectoryRecordVerifier`), а анти-откат действует только после
> первой принятой записи.

Отсюда: **скомпрометированный сервер не может подменить ключи** — ему нужен
второй прообраз SHA-256 (128 бит). Доверие сведено к строке адреса, полученной
вне сети, — то же допущение, что и для отсканированного QR.

### 4.8 Публичные алиасы (`@ник`) — опционально, по умолчанию ВЫКЛЮЧЕНО

`alias_index = HKDF-SHA512(salt="AEGIS/alias/v1", ikm=normalize(alias), info="aegis/alias/v1/index")`

- `PUT /v1/alias/{index}` — тело `{"claim":"<b64 каноничных байт>","sig":"<b64>"}`.
  Ответ `{"ok":true,"expiresAtMs":…}`; `409` — алиас занят другим ключом либо
  заявка не новее действующей; `400` — подпись/привязка/срок не прошли.
- `GET /v1/alias/{index}` — отдаёт `{"claim":…,"sig":…}` дословно или `404`.

Payload заявки:

```json
{ "v":1, "aliasIndex":"<b64u>", "accountId":"aegis:<hex>", "ed25519":"<hex>",
  "discoveryIndex":"<b64u>", "tagB64":"<b64 32B>", "nickname":"…",
  "issuedAtMs":0, "expiresAtMs":0 }
```

**Единственное место, где сервер проверяет криптографию** — и это не про доверие
к серверу, а про невозможность угона: без проверки любой перезаписал бы запись
`@alice` своей, а клиент, впервые ищущий этот ник, не смог бы отличить подмену
(закреплённого `accountId` у него ещё нет). Правило: свободный алиас занимает кто
угодно; занятый обновляет **только владелец того же ключа и только более свежей
заявкой** (`issuedAtMs` строго больше — иначе перехваченная старая заявка
«оживила» бы уже отозванный тег). Срок — не больше 90 суток, иначе алиас никогда
не освободится. Клиент перепроверяет подпись и привязку `accountId` сам.

**Перечислимость — осознанная граница.** Ник низкоэнтропиен, поэтому словарная
атака по индексу возможна принципиально; это свойство ПУБЛИЧНОГО имени. Утекает
только «такой ник существует и указывает на такой accountId» — ни ключей, ни
prekey-бандлов, ни того, кто кого искал. Сдерживание — proof-of-work
(`AEGIS_POW_BITS`), потому что лимит по IP за Tor бессмыслен (весь трафик идёт от
локального tor-демона с одного адреса):

```
epoch = floor(unix_secs / 600)
SHA-256("aegis/pow/v1" || path || epoch(u64 BE) || nonce) — не меньше N ведущих нулевых битов
заголовок: X-Aegis-Pow: <epoch>:<nonce-hex>       (годны epoch и epoch-1)
```

Не пройден PoW → `429` с текстом причины (клиент считает работу и повторяет).
Решение привязано к `path`, поэтому не переиспользуется на другом индексе; кэша
решений нет, так что для того же пути оно годно, пока действительны `epoch` и
`epoch-1` (10–20 минут). 20 бит по умолчанию — доли секунды на GPU.

> **Совместимость с клиентом 0.4.2:** клиент кладёт ключ в поле `ed25519Hex`, а
> релей требует `ed25519` — любая заявка клиента отвергается как некорректный
> JSON, поэтому публикация `@ника` сейчас не работает даже при
> `AEGIS_ALIAS_ENABLED=1`. Тесты релея этого не ловят: заявку они собирают сами.

### 4.9 `GET /v1/params` — возможности релея

Чтобы клиент не угадывал (иначе он считал бы PoW зря либо получал `400` и молча

## 5. Хранение и очистка

- Durable-очередь в SQLite (`AEGIS_DB`); конверты хранятся как
  `(mailbox, seq, data, ts)`. Дополнительно таблица `mailbox_seq` держит для
  каждого когда-либо использованного id ящика счётчик `next_seq` (сколько
  конвертов в него пришло за всё время) — она **не чистится никогда**: sweeper её
  не трогает, глобальные потолки на неё не распространяются (известное
  ограничение).
- Жёсткий потолок хранения — **7 суток** (§7.3): фоновый sweeper удаляет
  конверты старше `AEGIS_TTL_SECS` (кап `604800`).
- **Глобальные потолки диска** (`AEGIS_MAX_TOTAL_MESSAGES`,
  `AEGIS_MAX_TOTAL_BYTES`): `AEGIS_MAX_QUEUE` ограничивает лишь ОДНУ очередь,
  поэтому без глобальных лимитов дропы в неограниченное число новых ящиков
  забивали диск задолго до срабатывания TTL. При превышении вытесняются самые
  старые конверты по всей БД. Обратная сторона: при дефолтных 200 000 конвертов /
  512 МиБ анонимный клиент примерно за 8 000 дропов по 64 КиБ в новые ящики
  вытесняет все недоставленные сообщения всех пользователей; так же — вложения
  (1 ГиБ) и записи каталога (§6).
- Записи каталога и заявки на алиасы живут по **своему** сроку (`expires_at`,
  задаёт владелец) и подметаются тем же sweeper'ом.
- Логи — без содержимого и без идентификаторов пользователей (§7.6).

## 6. Границы (честно) и планы

- **v1 без серверной аутентификации мейлбокса.** Capability = знание mailbox-id.
  Недоверенный сервер и так не читает контент; DoS/доступность под zero-trust не
  гарантируются (это осознанный компромисс). Возможное усиление — подпись
  владения ящиком identity-ключом.
- **Ограничения частоты нет, вытеснение глобальное** (§5): любой, кто знает
  onion-адрес (он зашит в APK) или клирнет-домен, может дешёвым потоком дропов
  вытеснить чужие недоставленные конверты, вложения и записи каталога (после
  чего перестают работать адреса для удалённого добавления). Направления
  исправления: вытеснять в первую очередь из самых «тяжёлых» или новых ящиков,
  PoW или токены на запись в новый ящик, `HiddenServicePoWDefensesEnabled` в
  `torrc`, лимиты по IP в клирнет-профиле.
- **Метаданные от сервера** (§1): связывание ящиков через общую Tor-цепочку
  клиента и открытые поля конверта. Исправляется на клиенте — изоляцией потоков
  по ящику/контакту, разнесением опросов, переносом служебных полей внутрь
  шифрования и выравниванием длины; сервер менять не нужно.
- **Мелкие утечки.** `GET /v1/health` отдаёт глобальное число конвертов в
  очереди — оракул для анализа трафика. `PUT /v1/prekeys/{id}` перезаписывает
  любой, кто знает `id`. Подписи проверяются Ed25519 `verify`, а не
  `verify_strict`.
- **Доступность каталога не гарантируется.** Скомпрометированный сервер может
  удалить запись или не отдать заявку на алиас (отказ в обслуживании). Чего он
  НЕ может — подсунуть чужие ключи: подпись и коммитмент `accountId` проверяет
  клиент (§4.7).
- **Публичные алиасы перечислимы** (§4.8) — свойство публичного имени, а не
  дефект. Приватный путь по адресу (§4.7) неперечислим и остаётся основным.
- **Один long-poll на переписку.** Клиент держит по одному соединению на активный
  PSK-контакт плюс один на ящик приглашений. Вместе с общей Tor-цепочкой это и
  позволяет связать ящики одного клиента (§1). Для большого числа контактов — в
  планах мультиплексирование через единый аккаунт-мейлбокс.
- **TURN/медиа звонков через Tor** (§7.5) — РЕАЛИЗОВАНО (§4.5): coturn за отдельным
  onion + `GET /v1/turn`. Ограничение: реалтайм-медиа через Tor имеет высокую
  задержку/потери (осознанный компромисс режима Tor); UDP-TURN в этом режиме не
  используется. Клиенты без Tor получают клирнет STUN/TURN/TURNS того же coturn
  (`uris`). Кадровый слой поверх DTLS-SRTP включён в клиенте:
  `org.webrtc.FrameCryptor` (AES-128-GCM на ключах Signal+PSK) в той же
  native-библиотеке, что и WebRTC. См. `aegis-client/docs/calls.md §5`.
